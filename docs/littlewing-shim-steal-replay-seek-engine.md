# LittleWing: How to build snapshot seeking for replays

Report type: evaluation / review. It judges LittleWing's replay seek engine against 5 groups of open-source projects that solve the same engine problem: capture an emulator's state while it plays, then seek by restoring a nearby state and fast-forwarding to the target. It prescribes structures and patterns to adopt, in payoff order. The comparison is about how the engine is built, not what the user sees. It is the companion to [littlewing-shim-steal-replay-viewer-ui.md](littlewing-shim-steal-replay-viewer-ui.md) and deepens that report's Finding 3, which had medium confidence because it did not examine the emulator.

## Executive summary

LittleWing can't seek backward today. It restarts the process and replays from 0:00 at about 8x, which costs about 90 s from minute 14. The emulator has no way to save and restore its whole state in place. The good news is that most of that state already sits in one place: the guest's memory is a single host mmap at a fixed address that Unicorn maps by pointer, and the Memory Manager and QuickDraw keep most of their state inside it. Only six of the twenty modules with emulation state hold heap pointers or OS handles. So the right snapshot is a hybrid: raw guest pages, the Unicorn CPU context, and one small tagged block per host module, written through a Dolphin-style symmetric walker. Whole-process fork checkpoints are the wrong fit on macOS. Apple says frameworks are unsafe in a forked child, the core already calls CoreFoundation mid-game, and libTAS's macOS port is unfinished. Two risks need spikes before any storage gets built. A restore is only safe at a trap entry at nesting depth 1, and a seek from the end of a replay needs a way back into the guest. The HD twins are large (est. 40 to 120 MB at 4x) and depend on draw history.

### Key findings

1. **Snapshot guest memory raw, the CPU with `uc_context`, and each host module as one tagged block, as Dolphin, RetroArch and BizHawk's Waterbox do in parts.** Reject fork checkpoints. libTAS's own evidence argues against them on macOS. Confidence: high.
2. **Capture and restore only at a trap entry at depth 1, and build a re-entry path for seeks from the end, as Dolphin, libTAS and RetroArch confine state work to one clean boundary.** Confidence: medium.
3. **Make a seek a target tick the emulation loop polls, as BizHawk, FCEUX, Slippi, libTAS and asciinema-player do.** Skip the restore when the live state is closer, let the newest target replace the old one, cancel stale work with a generation counter, and restore play or pause at the end. Confidence: high.
4. **Prove every restore with a harness before trusting it, as BizHawk's integrity check, Dolphin's markers and RetroArch's netplay CRCs do.** Zero buffers before saving, put a marker and length check on every module block, and test that a seek across a snapshot reproduces the straight replay's frame hashes. Confidence: high.
5. **Keep snapshots in one budgeted arena with New, Mid and Old tiers and a guaranteed maximum gap, as BizHawk's PagedStateManager does.** Pin marks through an `is_reserved` callback. Confidence: medium.
6. **Share unchanged guest pages between snapshots, as RetroArch's statestream, Waterbox and libTAS do.** Prefer this to Slippi's deltas against the first state. Confidence: medium.
7. **Rebuild HD output after a restore instead of storing it in every snapshot, as libTAS and asciinema-player rebuild what can't be checkpointed.** Confidence: low.
8. **Suppress output at two layers during fast-forward, with RetroArch's invariant that skipping output changes no saved state.** BizHawk, FCEUX and libTAS do the same, and libTAS never skips while encoding. Confidence: medium.
9. **Keep everything on the emulation thread and send seek requests in as commands, as BizHawk, Dolphin and RetroArch do and Slippi doesn't.** Confidence: high.
10. **Keep snapshots in memory for the life of the process, as Dolphin's version churn and libTAS's process-lifetime states argue.** Persist them later only behind a build-ID header. Confidence: high.

## Amendments, 2026-10-17

A review of this report against the issues and the source changed four things, and a second review the same day, which checked the report's claims against the code, added five more. The findings stand as written; these notes say where the plan now departs from them, and #30, #44, #46 and #59 carry the same changes.

- **A persisted snapshot is a cache next to the recording, not a recording format** (Finding 10, #46). A snapshot is an image of guest memory, the game's code and resources included, and recordings are made to be shared (the High Scores menu, `FLAG_SHARED`). So it lives in its own file beside the `.lwreplay`. The recording keeps its session prefix and stays format 5, a share copies only the recording, and a cache whose header doesn't match is ignored and rebuilt, with the replay running from launch as before. The build-ID header stays: it is the cache's header. #46 first put the capture at a game's start during live play, where the audio callback thread is alive, which Finding 9's single-thread argument doesn't cover; the second review moved it to the first replay that reaches the game's start, below.
- **The store starts small** (Findings 5 and 6). A Loony game is 5 to 30 minutes, so 15-second spacing means 20 to 120 snapshots. v1 is fixed spacing, full copies of the resident pages, a hard byte cap, and thinning that drops every other old snapshot when the cap is hit. The tiers, the gap rule, `is_reserved` and page sharing were built for multi-hour TAS projects; they come only if step 1's measurements force them. Step 1 also spikes a copy-on-write remap of the guest region (`mach_vm_remap` with copy set, or `vm_copy`). If a capture can be a page-table operation and unchanged pages cost nothing across snapshots, Finding 6 isn't needed at all. That spike goes first among step 1's spikes, in #59's measurement pass, and it measures two things: the capture, and the page fault the live side then pays on its first write to each page. If it works, a capture costs milliseconds whatever the resident size, Finding 5's store is a list of regions, and snapshots can come every 5 s.
- **The mixer isn't what separates headless from the viewer** (Finding 8, D6, #59). `catch_up` (src/sound.c:88-97) returns early only when the live audio stream is open, and a replay never opens it, so the headless replay renders the mixer too and still runs at about 70x. The gap to the viewer's 8x is the HD sync on skipped presents, and the viewer's polling and quarter-second draws. #59 does the HD half first, measures with HD off too, and skips the mixer only if its measured share justifies the fidelity it costs. (Measured, below: nothing runs at 70x, and the HD sync was about 1% of a seek.)
- **Step 1 measures the depth-1 premise before any capture code.** Finding 2 rests on Loony's main loop running at depth 1, from reading the code. A histogram of `T.depth` at trap entries over a headless replay settles it in an hour, and goes first.
- **The game-start cache is written lazily** (Finding 10, #46). The first replay or export that reaches the game's start writes it, from the exact machine that will later restore it, and only that one pays the prelude, as every replay does today. Capturing during live play, which #46 first proposed, needs guest memory at the game's start to be byte-identical between live play and its own replay, and nothing verifies that: the frame hashes check the screen, not memory. A shared copy also swaps the license out of the prefs (`FLAG_SHARED`, `with_license` in src/replay.c), so the prefs block differs between copies of one recording. And it would run with the audio callback thread alive. Live capture stays a later option, with a test that live and replayed memory match.
- **A pending seek frees every host wait loop** (Finding 2, D4). The depth-1 trap-entry boundary stands, but the viewer spends almost all of its paused life inside a handler, not at an entry: `pace` inside the clock trap, `h_delay`'s loop (src/misc.c:275-294), `run_modal` during the high-score name entry (src/dialogs.c:600-613) and `watch_hold`. Finding 2 covers `pace` and `watch_hold`. The rule is general: a pending seek makes every one of those loops return and pacing free-run, so the guest reaches the next depth-1 trap entry and the seek is served there. In the dialog that means running until the recorded input closes it, at fast-forward speed: seconds of latency, not a bug, and Finding 2's longjmp re-entry is the escape if it ever matters. One correction to D4: the modal loop runs inside a depth-1 handler, not at depth 2. What rules it out is "not at a trap entry", not depth. #44 tests a seek requested while paused in that dialog.
- **After a restore** (Finding 1's `post_load`), three more things join the translation cache flush: mark the whole QuickDraw screen dirty so the window redraws at once, re-derive the viewer's clock and pacing anchor (`W.clock_us`, `anchor()` in src/watch.c) from the restored replay cursor, and rebuild or resync HD as Spike C decides.
- **A walker test that runs without the game** (Finding 4). The CI runner has no game, so every Loony test in this plan skips there (`SKIP_UNLESS_GAME`). The suite already assembles PowerPC for its register round trip (tests/test_cpu.c), so a synthetic-guest test can fill guest memory and every module's statics with known values, trap, snapshot, change them, restore, compare bytes, and run VERIFY so a mismatch names the module. It is the only check of the walker that runs on every push, and it catches the forgotten-field bug class Finding 1 names. #44 makes it a "done when".
- **The exporter keeps its HD sync unless Spike C passes** (Finding 8, D6, #59). The exporter's seek runs `hd_frame` on every present too (src/clip.c:617-623), and a clip's HD must be exact from its first frame. So #59's HD skip is viewer-only unless the one-shot sync at arrival matches a straight run at the same tick, which is Spike C's question. #59's result answers it, and says which.

## Measurements, 2026-10-17 (#59)

Step 1 ran, on a 20-minute headless recording of 11 Loony games (M4 Pro, Release build, SDL's dummy video driver, so no window; `LOONY_MEASURE=1` logs the sizes, and the viewer logs every unpaced stretch). Four of the report's premises change.

- **Loony's loop runs at depth 2, not depth 1.** Of 17,595,672 trap entries over the recording, 9,066 were at depth 1, 17,579,335 at depth 2 and 7,271 at depth 3 (sound callbacks). The game's `main` calls `RunApplicationEventLoop`, and everything after that, the opening and every game, runs in its event loop timer callback (code+0x23cc0, installed with `InstallEventLoopTimer`) from inside that handler (src/events.c:728-742). Finding 2's boundary has to be the trap entry at depth 2 inside that callback, with the handler's frames (`h_run_application_event_loop` and the timer dispatch) above it, or a re-entry that rebuilds them. Since 99.9% of entries are there, the simple form is: capture at a depth-2 trap entry inside the callback, restore only when the live process is at that same boundary, and snapshot the saved CPU context each nested `guest_call` holds, so the frames above the boundary match. Entries at depth 1 (the launch) and 3 (nested callbacks) are places where a seek waits. #44 starts here.
- **Output work isn't what bounds an unpaced replay; traps are.** The viewer going to a time ran the recording at 8.8x in HD and 17.7x without, and the headless replay at 7.0x in HD and 9.7x without (it presents every frame; the viewer draws four a second). The "about 70x" was never measured. Of the 18.0 s the viewer took to reach 2:00 in HD, the HD sync on skipped presents was 0.16 s, the mixer 0.02 s and drawing 0.11 s; over the whole recording the mixer was 0.11 s, polling 0.01 s and drawing 0.55 s of 136 s. HD doubles the time, but in `hd_copy` mirroring the game's CopyBits (about 137 a frame, each wrapped in ten more QuickDraw calls), which keeps the HD state and can't be skipped without Finding 7's rebuild. The rest is the trap rate: 14,700 trap entries a second of game time here, 83,000 in the attract mode, at about 4 µs each for Unicorn's start and stop. A cheaper trap path is the lever for speed, not output suppression (#68). Finding 8's HD half was built, measured at about 1%, and dropped before #59's PR merged (commit 64eca13 has it); its mixer half isn't built.
- **A capture is a page-table operation.** Guest memory is 9.2 MB resident of 97.0 MB mapped mid-game (the heap 8.9 of 64 MB, the image 0.3 of 15 MB). `mach_vm_remap` with copy set copies the whole mapping in 0.2 to 0.4 ms, `vm_copy` in 0.2 to 0.3 ms, and both copies hold every resident page exactly. The live side's first write to each resident page afterwards costs 1.7 to 2.3 µs, about 1.1 ms for all of them. So Finding 5's store is a list of regions, Finding 6 isn't needed, and snapshots can come every 5 s. A saved CPU context is 73,256 bytes. The HD copies are 220 at 4x, 30.1 MB, nearly all of it the screen.
- **Spike C passes for the viewer.** The HD screen after a seek, synced once from the 1x pixels at arrival, matched the straight run's at the same tick byte for byte, at four targets in two recordings, on the first frame after arrival and two seconds later. It was measured with the HD skip in place (commit ac36e8a holds the test); with the skip dropped, nothing in the tree syncs once, and #44's restore is where the result is used: keep the HD twins across a restore and let the normal sync redraw from the restored 1x screen, which makes Finding 7's rebuild recipe unnecessary for the screen. The viewer and the exporter both keep their per-present sync.

## Spike A, 2026-10-17 (#44)

Spike A passes. The emulator's state, captured at a depth-2 trap entry and put back in place at a later one, replays to the end of the recording with every frame check matching. `LOONY_SPIKE_A=<N>,<M>` (src/measure.c) captures at the first depth-2 trap entry past N seconds of the game's clock: the guest mapping with `vm_copy`, the CPU, the context each of the two nested `guest_call`s saved, and twenty blocks of module state registered with `MEASURE_STATE`. It restores at the first depth-2 entry past M that is in the same guest function, flushes Unicorn's translation cache and TLB, and dispatches the trap it captured, so the replay re-runs N to M and goes on. The setup was an 8-minute headless recording of four Loony games (soak script, unregistered, alerts answered, recorded on the real clock), replayed with HD off in the Debug build, so ASan and UBSan watched every restore. The games ran from 33 to 97 s, 102 to 205 s, 311 to 377 s, and 449 s to the end at 479 s.

|---|---|---|---|
| 10 to 25 | the opening | 25.0 s | no desync |
| 20 to 40 | the opening, to between games 1 and 2 | 97.4 s | no desync |
| 40 to 50 | game 1 | 50.0 s | no desync |
| 70 to 90 | game 1 | 90.0 s | no desync |
| 60 to 150 | game 1, to game 2 | 150.0 s | no desync |
| 150 to 330 | game 2, to game 3 | 330.0 s | no desync |
| 200 to 420 | game 2, to game 4 | 446.2 s, as game 4's handler began | no desync |

Each reached the end of the recording at tick 28741 with all 908 frame checks matching. `run_spike_a_restores_a_game_in_place` (tests/test_run.c, slow) records a one-minute game and runs the spike at 10 to 25, 40 to 50 and 45 to 55.

- **Loony's games don't run in the timer callback.** The opening, the menus and the time between games run in the event loop timer's callback (code+0x23cc0), as #59 found. Each game runs in a Carbon event handler (code+0x23d40) that the event loop dispatches from its queue (`dispatch` and `run_handlers` in src/events.c), and that one call lasts the whole game. Both are at depth 2, so #59's histogram couldn't tell them apart. The host frames above them differ: above the handler are `dispatch` and `run_handlers`, holding the event's slot and the handler's index; above the timer callback is `fire_due_timers`, holding the timer's index. So the boundary is a depth-2 entry in a given callback. The spike records the guest function its depth-2 `guest_call` entered and restores only into the same one. That is why the capture in the opening at 20 s waited until game 1 ended at 97 s, the next entry in the timer callback, and the capture in game 2 at 200 s waited out the time between games 3 and 4.
- **Which means a seek can't always cross between the two.** A snapshot taken in a game restores from inside any game, here across three of them. One taken between games restores only from between games. A seek from inside a game to the opening, or from between games into a game, has to wait for the live process to cross over, which can be minutes, or never if the recording ends first. The engine needs a way to switch frames: unwind the host to `h_run_application_event_loop` and re-enter the other kind of call with the snapshot's saved contexts. That is the report's re-entry path (Finding 2), needed mid-replay and not only at the end. It is the common case, not the edge: the viewer's timeline shows play time only, so every seek target is inside a game, while a replay that has reached its end is between games or past `main`, and a replay starting from #46's game-start cache is at launch. Spike B (#44, "Spike B, exactly") is that re-entry: capture inside a game, let the replay end, rebuild the event loop frames from `main` with a resumable `guest_call` and a resumable `h_run_application_event_loop`, and run to the end again through a game's ending. The frames' own values (the event's slot, the handler's index, the timer's index) belong in the snapshot too. They matched in every run here across different calls of the same callback, but nothing checked them: an event takes the lowest free slot, so the game's event lands in the same slot whenever the queue is otherwise empty.
- **Two modules needed real copies, not crude ones.** The mixer frees a sound when it finishes, so the crude copy handed back freed `mix_sound`s. ASan caught the heap-use-after-free in `sample_at` on the first in-game run. Its copy now clones every channel's voice and queued sounds (`MEASURE_STATE_WITH` in src/mixer.c). The Resource Manager wasn't among the six pointer-holding modules this report lists, but each `rsrc_entry` caches the guest handle its resource was loaded into, in a host array. Restored without it, `GetResource('Song', 128)` returned a handle the restored heap no longer had, and `HLock` crashed. Its copy now includes the entries. cf, dialogs, cgimage and files were copied crudely, pointers included, and held in every run, including restores across the end of a game. So the inventory is the report's twenty modules, with rsrc moved among the pointer holders, and the issue's first suspect, the mixer, was the first failure.
- **What the twenty blocks are.** misc (`M` and the system version), events, qd, memmgr's last error, trap, rsrc, script, play, replay, sound, mixer, cf, files, dialogs, plus cgimage, cgdisplay, cxxrt and libc's two blocks, which only MONSTER FAIR uses: 314 KB in all. Left out as host-only or derived: hd, display, watch, clip, export, picker, recordings, the menu bar, font's glyph cache, and scratch statics inside functions (blit's pixel map, libc's sprintf buffer).
- **Timing.** A capture took 0.37 to 0.58 ms, and 2.0 ms once with five replays sharing the machine: the mapping 0.15 to 0.5 ms, the CPU and both saved contexts 0.03 to 0.06 ms, the module blocks 0.05 to 0.18 ms. A restore took 0.2 to 0.56 ms, of which `vm_copy` back over the live mapping was 0.07 to 0.36 ms. Debug build, with sanitizers.
- **Not covered.** HD on (Spike C covers the screen), the viewer's clock and anchor after a restore, a seek requested from inside a handler, and Crystal Caliburn and MONSTER FAIR.

## Spike B, 2026-10-17 (#44)

Spike B passes. A snapshot taken inside a game's handler restores from a different host frame, with no guest call on the host stack, by rebuilding the frames above it; the game runs on, its handler returns to the rebuilt run loop, and the replay reaches its end a second time with every frame check matching. `LOONY_SPIKE_B=<N>` (src/measure.c) captures as Spike A does at the first depth-2 trap entry past N seconds inside a handler `RunApplicationEventLoop` dispatched to, adding the trap depth 1 is in and the run loop's dispatch: the event's slot, the dispatch chain and which target it is on, the handler's index, and the loop depth `call_out` hid. When the game ends inside a trap, the spike longjmps to a `setjmp` in `main`, frees the unwound levels' contexts (`trap_unwind`), restores memory and the module blocks, and calls `guest_resume` for depth 1: a `guest_call` that adopts the snapshot's saved context and dispatches the `RunApplicationEventLoop` trap it recorded. That handler, told to resume (`events_resume_loop`), skips its setup and goes straight back into the recorded dispatch, which calls a second `guest_resume` for the game's handler at the captured trap. From there every loop is the normal one. In every capture the game's event was in slot 0, going to handler 2 on the application target, the second of two targets (the focus window's handlers come first for a keyboard event, so the game runs inside the Return key's handler), with loop depth 1.

The recordings were made headless with the soak script, unregistered, on the real clock: two of 8 minutes, one ending with the script's quit (games at 33 to 135 s and 311 to 413 s) and one cut off by `LOONY_EXIT_AFTER` at tick 27500, inside game 5 (games at 33 to 135, 241 to 306, 311 to 376, 380 to 445 and 449 s to the end); copies of the second cut short; and two of 150 s with one game (33 to 146 s), one quitting and one cut off between games. - **Nothing was missing from the frames.** The issue's likely failure, the handler's return rejoining the event loop with a value the snapshot lacked or a `release` or timer step running twice, didn't happen in any run. The frame values above are all it took, and the event's reference count, the timers and the quit flag came back right inside the restored events block. So the walker's snapshot holds, per level, the context its `guest_call` saved, the function it called, and the trap it is in with its resume address, plus the run loop's dispatch frame.
- **Loony's `main` never returns.** Its quit Apple Event handler calls `QuitApplicationEventLoop`, `RunApplicationEventLoop` returns, and `main` calls ExitToShell at depth 1. So the depth-0 end the issue planned for first doesn't occur in Loony; ExitToShell does, and it comes through misc's exit hook, `back_to_picker` in src/main.c, which is where the spike catches every end (`measure_game_ended`). The depth-0 path is there, re-entering directly with no longjmp, but no run here took it.
- **The end comes in four kinds of frame, and all of them re-enter.** ExitToShell at depth 1, outside the run loop; the recording's end in the run loop's own pump at depth 1; in the timer callback at depth 2; and inside a game's handler at depth 2. Since the re-entry always starts from `main`, where the live process was doesn't matter, only that no guest call is left on the host stack. That is also the answer for #46: a replay starting from the game-start cache, at launch, enters a game the same way.
- **What describes the host stack has to live outside the module blocks.** The trap depth moved out of `T`, next to the saved contexts, since a crude copy of `T` put back a depth that no longer matched the host stack. events.c's pointer to the run loop's dispatch in progress is the same kind of value, and after the longjmp it points into a dead frame; the spike gets away with it because the resumed run loop sets it again, but the walker needs an unwind step that resets every such value (events, and trap's per-level arrays).
- **The game's clock isn't readable at the recording's end.** misc stores the host's time in `M.last_us` and only then asks the replay for the recorded time, and the end fires in between, so `misc_last_seconds` there gave 156.6 s of wall time at what was 458 s of play. The seek controller should take the time from the replay's cursor, not from misc, which is what the issue's "after a restore" already says for the viewer's clock.
- **Timing.** A capture took 0.45 to 1.0 ms; a re-entry's memory restore 0.3 to 0.77 ms, of which the mapping was 0.09 to 0.45 ms. Debug build, with sanitizers, up to nine replays sharing the machine.

## The seek controller, 2026-10-18 (#44, PR #73)

PR 1 of #44's build order is merged: going back in the viewer puts back a snapshot instead of restarting the program. While watching, src/seek.c takes a snapshot (src/snapshot.c, grown out of the spikes' code) at the first depth-2 trap entry every 5 s of the replay's clock, in either of the two frames the run loop calls the game from: a handler it dispatched an event to, or a timer its own pump fired. A seek (`seek_to`, newest wins, with a generation counter) is served at the next depth-2 trap entry through the trap entry hook: the last snapshot at or before the time wanted goes back in place when the live frame matches (`snapshot_fits`), and otherwise the replay unwinds to `main` with a longjmp and re-enters as Spike B did, now into a timer's callback as well as a dispatch. A pending seek ends every wait the viewer has (pacing, the pause, the end hold), so the replay reaches that entry unpaced; `misc_wait` already returns at once during a replay, so the modal dialog's loop spins at full speed too. From the snapshot the viewer replays to the time unpaced, with the pause, the speed, a clip's start and a running export kept.

The store keeps at most 120 snapshots in the clock's order, about 0.9 MB each as copy-on-write regions, and thins out the one whose neighbours are closest when the cap is passed, so the oldest end up 10 s apart, then 20. Outside play only the latest of each stretch is kept, since every time the viewer goes to is in play. After a back seek into a thinned region, snapshots are taken again at 5 s spacing and the thinning runs again; harmless, bounded by the cap.

| | |
|---|---|
| A capture | 0.24 to 0.34 ms |
| A restore in place | 0.20 ms, then 1.2 s of game time replayed in 0.02 s |
| A re-entry from ExitToShell after the end | 0.21 ms, then 4.7 s replayed in 0.05 s |
| Peak footprint, snapshots on and off | 115.1 and 96.8 MB for 21 kept, so about 105 MB at the cap |
| Replay speed | 10.7x either way |

Release build, HD off, headless, on a 170 s recording of one game.

- **The walker's inventory grew.** Besides the mixer and the Resource Manager (Spike A), dialogs (saved screens and nibs) and Core Foundation (its object array and every string) needed real save, load and drop functions, since a crude copy would hand back freed pointers after a dialog closed or an object was released. Sound keeps its host fields (streams, volume, WAV output, the tap) across a restore. The script's state left the inventory: a script's keys follow the replay's clock, so after going back the next one comes when the clock reaches it again. `load` no longer consumes the copy, so a snapshot can be put back any number of times. The rule is now in CLAUDE.md: guest-visible module state is registered with `SNAPSHOT_STATE`, with save, load and drop when it owns heap objects that come and go.
- **The unwind step exists.** `trap_unwind` clears the per-level arrays and `events_unwind` the frame in progress and a resume not taken up, as Spike B said they must.
- **The screen redraws from the viewer's own flag**, not QuickDraw's dirty flag, which would shift the frame checks.
- **Still copied crudely:** files.c's open files and cgimage's images. Neither changes during a Loony replay. PR 2's walker takes them.
- **HD after a restore:** HD's copies of offscreen buffers keep what they had after the capture until their next use, when `hd_copy` syncs the source copy from its 1x pixels before copying from it. The remaining question is which art that sync picks for the changed pixels, which is #44's done-when 6, in PR 2, and worth one run by hand in HD before the next release.

## The hardening pass, 2026-10-18 (#44, PR #76)

PR 2 of #44's build order is merged, and with it "done when" 3, 4 and 6. The snapshot's module state is one buffer now, not a heap copy per block: a header (magic, version, a hash of the inventory's layout, the block count), then a block per registered variable with its tag (a hash of file and name), its struct size and its length. A module that holds pointers or host fields registers a single walk (`SNAPSHOT_STATE_WALK`) that runs both ways, saving and loading, so the two can't drift apart: `snapshot_bytes` for the game's bytes, `SNAPSHOT_OWNED` and `snapshot_string` for heap objects the block owns (copied on save, allocated fresh on load), `SNAPSHOT_HOST` for the host's fields (zeros in the snapshot, kept on load through a stash of the live bytes), `SNAPSHOT_REBUILT` for what the walk rebuilds itself, `SNAPSHOT_PADDING` for heap padding. The buffer is zeroed as it grows and pointers are written as zeros, so two snapshots of one state are the same bytes. Loading fails hard and names the block on any header, tag, size or length that doesn't match. That header and layout hash are what #46 needs for a snapshot on disk.

Every module with pointers has a walk now. mixer, cf and dialogs were converted from save, load and drop. sound's eight host fields are `SNAPSHOT_HOST`. rsrc walks only ResError and each entry's guest handle, and checks the entry and type counts against the parsed fork, which stays the host's. replay, events, trap, misc and qd had been crude copies of host pointers that never change; those are host fields now. files and cgimage, crude until here, are real: an open file is its name, folder and mark, reopened on load (a file's contents aren't in a snapshot), and a CG object is its provider path or its pixels. Two pointers into the shim's own statics are left as they are, events' modal sink and dialogs' front dialog; on disk they would have to become indices. The mixer's walk needs no lock: a replay opens no device stream, and the viewer's monitor is a push stream the main thread feeds, so nothing renders from another thread while a snapshot exists.

`LOONY_SNAPSHOT_VERIFY=1` (README) checks the snapshots as they are used. Each one is put back the moment it is taken and compared with the emulator. After a seek, the replay is compared with every snapshot it passed before, at the exact trap entry where that one was taken: `trap_entries()` counts the guest's trap entries on the game's timeline, is restored with a snapshot, and doesn't count a resumed dispatch, so it names one entry of a replay however the replay got there. The comparison covers guest memory page by page (only pages `mincore` says either side holds), the CPU and the saved contexts register by register (`cpu_context_same`), the frame, the clock and each module block, and names the first byte that differs ("misc.c M at byte 16 of 136"). A difference is fatal. An unwatched replay takes snapshots too while verifying, so its output can be compared with one that takes none.

## The game-start snapshot's size, 2026-10-18 (#46, step 1)

#46 plans to put a snapshot of the game's start in the recording, stored as a delta against a baseline that every replay passes shortly after launch, so a game's replay can start at the game. Step 1 measured that before building it. `LOONY_MEASURE_DELTA=<folder>` (src/measure.c) writes every resident page of the guest mapping, with its offset, at the baseline and at the game's start, and exits; `LOONY_MEASURE_DELTA_AT=<seconds>` moves the baseline later. `tools/measure_delta.py` counts and compresses them. The baseline is the first depth-2 trap entry inside the run loop's timer callback (at or past the given time), and the game's start is the first depth-2 entry inside a handler the run loop dispatched to once the file's first span of play has begun. That is where #46 would take the snapshot.

There were three recordings, each with a game at a different distance from launch: a session's first game, unregistered (soak script, 33 s in); the fourth game of an unregistered soak session (380 s in); and a registered game the user played on 2026-10-16, 2,705 s (45 minutes) into its session, the late game the issue asks for. The soak session stalled after its fourth game (the script's keys stopped starting games after a game over), so the 45-minute recording stands in for the ten-game session. Release build, headless, HD off, replays sometimes sharing the machine. Sizes are zstd at level 3, then level 19, of the pages with their offsets; a delta is the pages that differ from the baseline, XORed with the baseline's page where it has one.

| | Game 1, 33 s in | Game 4, 380 s in | 45 min in |
|---|---|---|---|
| The recording | 12.8 KB | 54.4 KB | 860.8 KB |
| Replay from launch to the game's start | 7.6 s | 43 s | 149 s |
| Resident at the game's start | 592 pages of 16 KB, 9.7 MB | the same | the same |
| Whole | 2.97 MB, 2.64 MB | 2.97, 2.64 | 2.97, 2.64 |
| Delta from the first timer callback (0.19 s in) | 1.07 MB, 0.92 MB | 1.07, 0.92 | 1.07, 0.92 |
| Delta from the first callback past 8 s | 0.53 MB, 0.47 MB | 0.54, 0.48 | 0.51, 0.47 |
| The same, less the game's own sounds and art | 118 KB, 98 KB | 120, 100 | 152, 125 |

The replay reached the first timer callback 0.19 to 0.21 s after the process started, and the one past 8 s of its clock at 0.26 s, loading the program included: the opening waits on its splash screen, so the first 8 s of game time cost 0.06 s. Past 8 s the opening is in its attract loop, at about 3x, and 16 s costs 2.8 s. In the two runs that checked, no page `mincore` left out held anything but zeros, so the resident pages are the whole state.

- **The delta doesn't grow with the session.** The game's start is the same 592 pages whether the game comes 33 s or 45 minutes after launch, and the whole set and the delta are nearly the same size in all three. What changes between launch and a game's start is one game's heap, the screen buffers and what the opening loads, as the issue guessed, and earlier games leave nothing behind. What grows is the prelude the snapshot saves: 149 s for the late game, at 18x.
- **The first timer callback is too early for a baseline.** At 0.19 s the opening has 441 pages resident, and 503 from 1 s on. A baseline at 1, 2 or 4 s leaves the delta at 0.84 to 1.09 MB; between 4 and 8 s the opening writes what the game's start still holds, and a baseline past 8 s halves the delta, for 0.06 s more replay. Later ones don't help: at 16 s game 1's delta is a little larger again (0.55 MB), the attract loop having moved the heap on.
- **The delta still holds the game's sounds.** Of the late game's 235 differing pages, 34 are mostly bytes copied verbatim from the game's resource fork, about 0.5 MB raw: nearly all of it `snd ` 10003 to 10008, the rest `TiTl` 800 and 801 and `ViDe` 904. They differ from the baseline because they were loaded after it, at addresses that depend on the session's heap. They are 70% of the compressed delta, since sound compresses poorly, and they are the game's own content, which a shared recording must not carry (the reason the delta exists). Left out, and loaded again from the fork on restore (rsrc's walk already holds each entry's guest handle), the delta is 118 to 152 KB.
- **The baseline is a function of the recording, not only of the game files.** At the first callback, two sessions differ in 3 of 441 pages; at 8 s, two unregistered sessions differ in 2 of 503 and a registered one differs from them in 95 (registration changes the opening). That doesn't break the design: a snapshot is only applied to a replay of its own recording, which reproduces its own baseline from its prefix on any machine with the same game files. But the issue's identity (game ID, game file hash, guest layout, inventory hash) isn't the right check for it. A hash of the baseline's pages is: stored in the snapshot's header and compared with the live pages when the replay reaches the baseline, it catches another game file, layout or shim change that moves memory, by what actually matters. The module inventory's hash is still needed for the module blocks.
- **The whole set is too big to ship, even without the sounds.** Leaving the verbatim game-file pages out of the whole set still leaves 2.1 MB (1.8 at level 19): most of the state is decoded art, pixels in the offscreen buffers, which no resource holds. So the baseline is worth its code: 2.1 MB against 0.15.

**Decision:** build the delta, with the baseline at the first timer callback entry past 8 s of the replay's clock, and leave out loaded resources that are unchanged since they were read, filling them in from the fork on restore. That makes the late game's snapshot about 150 KB, a sixth of its recording, reached in 0.26 s. A delta that keeps the resources is the simpler first step at about 0.5 MB, but it puts the game's sounds into shared files. The baseline's identity is a hash of its pages. Plan B, reloading the guest at every game's end, isn't needed. One thing to decide while building it: whether a game near launch needs a snapshot at all. The first game's prelude is a few seconds, and its snapshot would be nine times its recording.

## The game-start snapshot, built, 2026-10-18 (#46)

#46 is built as step 1 decided. A replay of a recording with no usable snapshot keeps an in-memory snapshot at the baseline (the first depth-2 trap entry inside the run loop's timer callback past 8 s), takes another at the game's start (the first depth-2 entry inside a dispatched handler once the first span of play has begun), and writes the second into the recording as a delta against the first. Every replay after that reaches the baseline, checks the snapshot's header, decodes it against guest memory there, and goes to it from main through the seek controller's re-entry path (`seek_enter`, `snapshot_reenter`). src/gamestart.c holds the module, and its header is the specification.

- **The file.** Format 6 is format 5 with an optional section after the end record, found by a trailer (its length and `LWSTART6`), so the records keep their offsets and a format 5 file reads as before. The section is a header (the build's LC_UUID, the recording's identity, the baseline's clock, trap entry and SHA-256 of its non-zero pages, the start's clock and trap entry, and the resources left out) and `snapshot_encode`'s bytes: the CPU and both levels' saved contexts as their 71 machine registers (`cpu_context_regs`, written over a live context on load, since a `uc_context` is Unicorn's raw `env` and holds host pointers), the frame, the clock, the module state as is, and every page that differs from the baseline, XORed with it; then an HMAC (below). A page counts as held when `mincore` says it is in memory or paged out, since a compressed page reported as absent would be encoded as zeros and the snapshot be wrong for good. Adding a snapshot rewrites the file through a hidden temporary with the termination signals blocked, giving the temporary the file's mode, extended attributes and last write's time before the rename, so no moment shows another time: that time is how a recording is matched to its high score.
- **What made the module state portable.** Five fields meant something only in the process that wrote them: files' game and data folders, cf's preferences path (the replay's own temporary folder), events' modal sink and dialogs' front dialog. The folders are host fields now, the sink is walked as whether there is one (loading takes dialogs' sink back), and the front dialog as an index. The replay's own block made a snapshot specific to one file's header, so the header is a host field and the read position is walked relative to where the records start. The identity hashes everything a replay sees except the shared flag and the license, with the preferences normalized as a shared copy has them. So a recording and its shared copy have the same identity, and one's snapshot fits the other: before snapshots were signed (below), a shared copy of the 45-minute recording, with a header of another length, went to the game from the original's snapshot and ended on the same last frame.
- **The license is never in a snapshot.** The game copies the e-mail address at launch into its globals (0x00148808 here) and keeps the key code in no text form, both before the baseline, so the XOR leaves them out of the pages. cf's state held them as CF strings: `cf_keep_out_of_snapshots` names the license keys, and a string equal to one of their values as loaded is walked as which key it is and filled back from this process's preferences on load. At capture, the snapshot's plain pages are scanned for either string wherever they differ from the baseline's, since the XOR would hide a copy the game wrote later, and `replay_set_snapshot` and `replay_share` both refuse a section with either string in it, as it is or in capitals or small letters, as a backstop.
- **Resources.** At capture, every loaded resource whose bytes in guest memory still match the fork is written as the baseline's bytes and listed (index, address, length); on load, the fork's bytes go back there (`snapshot_poke`). For Loony's game start that is 12 resources, 1.06 MB, the sounds and art step 1 found.

- **Verified.** `LOONY_SNAPSHOT_VERIFY=1` decodes the snapshot at the baseline and doesn't use it, plays from launch, and compares it with the emulator at the trap entry where it was taken. It matched byte for byte, resources refilled included, on both recordings above, the Debug build's snapshot in the Debug build and the Release build's in Release. A second replay from the snapshot reached the same step, with the same last frame, as the straight replay. `run_a_recorded_game_starts_at_the_game_from_its_snapshot` checks the same on a recorded game, plus a damaged baseline hash (refused with a log line, the replay plays from launch and takes the snapshot again) and `LOONY_GAMESTART=0`. tests/test_snapshot.c and tests/test_replay.c round-trip the encoding, the license scrub, the section, the identity and the share in CI.
- **The exporter (D7).** A clip export of the 407 s recording's mark took 8.0 s from the snapshot and 18.3 s from launch, and the two files differ only in the 11 bytes of the MP4 headers' creation times, as two exports from launch do. That needed one change: clip's sound tap counted the frames it was handed since launch, which a replay that skips the prelude never renders, so the tap now says where its frames are on the game's sound timeline (`SND.rendered`, which is in the snapshot). A clip whose first tick comes before the snapshot's clock replays from launch (`gamestart_limit`), so an export stays frame-exact.
- **Only this install's snapshots are used, so a shared copy carries none.** This is a departure from the issue, which wanted a shared copy to start at the game on the recipient's Mac too, and it was built that way first: the share copied the section, and when the recording had none the menu ran a second copy of LittleWing (`LOONY_GAMESTART=take`) on the shared copy before the share sheet, 77 s for a game 1,178 s into its session. A review then pointed out what that trusts. A section is the whole emulator: guest memory and all 71 registers, the program counter among them, and every module's state. Every header check (the build's UUID, the identity, the baseline's clock, trap entry and hash) can be computed by anyone with the same game and build, so a crafted `.lwreplay` that someone double-clicks would run whatever PowerPC code it holds against the more than 200 trap handlers written for one cooperative program, and load counts, ring indices and relative paths into host statics that index host arrays and open files. Validating the module state on load would close the second and not the first. So each section ends with an HMAC-SHA256 under a key the install makes at first use (`snapshot.key`, mode 0600, beside the games' save folders, never in a replay's own `LOONY_DATA_DIR`), a section without a valid one is ignored like any other mismatch, and `replay_share` leaves the section out. A recipient's first replay pays the prelude once and keeps its own. Trusting a shared snapshot would need either a guest sandbox the shim doesn't have, or a hardened trap layer plus a load-time check of every value in every block; the portability above is what that would build on. The baseline also holds the license the game copied at launch, so even then a shared snapshot would fit only a viewer registered with the same license.
- **The build ID** is the program's LC_UUID, so every build ignores the snapshots of every other and takes its own on the next replay. That is strict for a developer, whose rebuilds each invalidate them, and safe: the build is what decides the module state's meaning.
- **The step 1 spike is gone:** `LOONY_MEASURE_DELTA` and tools/measure_delta.py.

## The game-start snapshot, shared, 2026-10-18 (#46)

The owner decided to accept what the entry above declined: a shared copy carries its snapshot, and any install's snapshot is used. A snapshot is an emulator save state, which every emulator loads from files it didn't write; the trap handlers bounds-check guest ranges; and the audience is people sharing pinball replays. So the signature went, `replay_share` keeps the section, and a share of a recording without a snapshot takes one first. What was built in its place is cheap hygiene, not a sandbox.

- **The license in the baseline.** The baseline hash refused every foreign snapshot, since the baseline holds the license the game read at launch. The disassembly (tools/disasm.py, `CInternetPreference::Load` at code+0x0f050) shows where. Loony copies "user email" into a 256-byte global (0x00148808) and "user id" into a 64-byte one (0x001487c8) with `CFStringGetCString`. It then decrypts the key code in place with the machine signature (`TAuthorize::DecryptAuthorizeString`), so that buffer holds a string no preference holds, and blanking the license's text alone would not have been enough. Next, the verify functions build license-derived strings in stack buffers. A throwaway write hook over every guest write made from the license code (code+0x0e040 to 0x0f294), compared with memory at the baseline of the 45-minute recording, found nothing of theirs surviving but saved registers, back chains and zeros. The rest was overwritten before 8 s. So cf now notes every guest buffer it copies a license string into (`cf_kept_out_fields`: the two globals, and a 64-byte stack buffer another path copies the e-mail into), at the size the game gave. The hash blanks those buffers, and the license's text wherever else it is, in any case. Without a second valid Loony key, the end-to-end check is a unit test in which two licenses of different lengths, copied in and changed in place, hash alike.
- **The checks on a snapshot from a file.** `snapshot_brings_no_code` requires the following. The decoded memory equals the live baseline's across the code section, which the recipient's own game files filled; resource refills are applied before the check, so they can't write there either. Every pc, lr and ctr (the CPU's and each level's saved context), and each level's function and return address, is in the code section, at an import's trap address, at guest_call's return address, or zero. Each level's trap is an import, and depth 1 is `RunApplicationEventLoop`. The machine state register is the live CPU's. The frame's indices are range-checked at decode. A refusal is a log line and a replay from launch. Every module walk then checks what it loads (`snapshot_check`): ring heads and counts, handler and item counts, frame consistency against the events state, cf's counts against capacities and preferences against objects, dialog item indices and the saved screen's rectangle, mixer queues, sounds and volumes. Paths may name nothing outside the shim's folders or the bundle. Fields that are the host's and never the game's became host fields: the import count and code range, the replay's mode, paths and parse results, `LOONY_EXIT_AFTER`, `LOONY_FIXED_CLOCK`, `LOONY_AUTO_ALERTS`, play's flags and libc's program path. Several of those were also portability bugs: the recorder's `exit_after`, executable path or recording paths would have been loaded into the viewer. A check that fails at load is fatal and names the block, as the front dialog and the replay cursor already were. The one value left unchecked is sound's `rendered`, which can only cost time, as crafted guest data can anyway.
- **Only the code section is executable.** The image region was mapped RWX whole, so a crafted transition vector in the data section could have sent the game's own indirect calls into bytes a snapshot brought. main.c now maps everything in the image but the code section read-write only (`cpu_no_exec`; PEF sections are 4 KB aligned). The 45-minute recording replayed from launch to its end with no desync under it, and the slow suite passes.
- **Taking one for a share.** `LOONY_GAMESTART=take` replays until the snapshot is kept, found or ruled out, then exits. The High Scores menu's Share and Save run it on the shared copy (`gamestart_take_start`, headless, silent, HD off) behind a panel with Cancel, and then show the share sheet or the save panel. The snapshot comes from the shared copy because the recipient replays that, with the sharer's license swapped in. `run_a_shared_game_starts_at_the_game_on_another_install` records a registered game, shares it, and takes the snapshot under one home folder through that child. Replayed under another home folder, it goes to the game's start and ends on the same frame, after the same frame checks, as a replay of it from launch.
- **The status-2 exit of `run_a_watched_game_goes_back`** (PR #79's review). Looped 12 times, it failed once. The test runner now prints a failing test's child output, and that showed `LOONY_SNAPSHOT_VERIFY` stopping the replay at 170.478 s: "events.c E at byte 5688 of 5720", which is `E.quit_deadline`. The game quits just before the recording ends. The quit Apple Event sets that deadline to the host's wall clock plus 3 s, and a snapshot taken after it holds that wall time. A replay that goes back and comes to the same snapshot again holds a different one. Whether a snapshot lands after the quit depends on timing, hence the rare failure. The deadline is only enforced outside replays, and what the game sees is whether a quit is pending, so the walk keeps that flag and sets the deadline again from this process's clock on load. It was also a value from another process's clock in a shared snapshot. The next 24 runs failed twice more, both in the test itself. Its recording is made on the real clock, so the game ends anywhere from about tick 9450 to 9550, and the recording stops 1 to 104 ticks after the quit at 10200. Its J "between games" at 9500 once came during play, and its J "after the end" at 10300 once came before the end. Each time the replay did the right thing for where it was. Those keys are at 9900 and 20000 now, and the test runner prints the last children's output of any failing test, whatever their status.
- **Numbers.** In the Debug build (sanitizers), the 45-minute recording replays from launch in 533 s and from its snapshot in 16 s, going to the game's start 0.57 s after the process starts. The test's game, 33 s into its session, takes its snapshot in 21 s.

## Method

I profiled the subject first, at commit c63f43a, through eight structural lenses: state capture, save/load symmetry, storage and budget, seek algorithm, determinism and verification, threading and process model, invalidation, and messes. The references were chosen for the engine problem, not the UI. Each one captures emulator or player state and seeks by restoring it, or is the strongest example of a capture technique LittleWing might use. Parallel dives read each reference at a pinned commit, organized by the same eight lenses, and cited every behavior to the file and lines that implement it. Each dive opened every range it cited. Nothing in any reference was built or run. Synthesis mapped shared patterns to named subject deficits and ranked them by deficit severity, then how many references agree, then cost.

I reconsidered the UI report's five references. LosslessCut, uosc and IINA seek through a media decoder, which has no emulator state to capture, so they drop out. I kept Slippi, because it is the only one that snapshots a running emulator to seek a replay, and asciinema-player, because its segments and generation counter are the cleanest single-threaded seek design in the set. I added Dolphin for per-module serialization, BizHawk and FCEUX for snapshot storage and TAS seeking, RetroArch for tagged state containers, deltas and output suppression, and libTAS for whole-process checkpoints.

A final pass opened every citation in this report, the permalinks against the pinned clones and the subject lines against the repo at c63f43a. It checked 216 citations (133 reference permalinks and 83 subject lines): 206 passed as written, 10 were corrected (wrong lines, or a claim reworded to say only what the code shows), and none were dropped. Sizes marked "est." are estimates from the subject profile, not measurements. One reference clone, RetroArch's, carries an AGENTS.md (contributor style rules) and a CLAUDE.md that includes it. The dive recorded them and did not act on them.

## Baseline: where the subject stands

LittleWing runs a PowerPC Mac game under Unicorn, with the Mac Toolbox reimplemented in C modules on the host. The guest owns the main loop. `main` calls `guest_call(img.main_tvector)` and returns only when the game's `main` returns (src/main.c:470-475). `guest_call` loops `cpu_run`, dispatches a trap to its handler, and resumes (src/trap.c:155-232). The host only runs inside those handlers: the event pump, presents, pacing, the paused viewer loop and menu callbacks all happen there. A replay feeds back the clock, input and sound callbacks from its file, and checks a frame hash every 30 presents.

Deficits the findings map to, worst first:

- **D1, a back seek restarts the process.** `go_back` sets environment variables and calls `W.restart` (src/watch.c:324-349). `restart_watching` deletes prefs.plist and `restart_self` calls `execv` (src/main.c:164-180, 200-206). The new process reloads everything and replays from launch.
- **D2, no whole-state save or restore.** `cpu_save` and `cpu_restore` wrap `uc_context_save` and cover registers only (src/cpu_unicorn.c:212-225). The one round-trip test covers registers only (tests/test_cpu.c:119-129).
- **D3, emulation state is spread over twenty modules' file-scope statics, with no inventory.** Fourteen are plain fixed-size structs. cf, dialogs, cgimage, files, mixer and hd hold heap pointers or OS handles, such as `FILE*` in `F.files` (src/files.c:48-57) and cf's object array (src/cf.c:31-46).
- **D4, no defined safe point.** Host C frames above the depth-1 `guest_call` hold live locals, for example `h_delay`'s `end` (src/misc.c:275-294). The guest re-enters from handlers for sound callbacks, timers and qsort (src/sound.c:297, src/events.c:348-354, src/libc.c:189). Menu actions arrive inside `SDL_PollEvent` (src/menu.m:217-233). At the end of a replay, `watch_hold` loops forever, either after `main` returned or inside a trap via `replay_step` (src/replay.c:1044-1061, src/watch.c:692-712).
- **D5, HD state is large, history-dependent and keyed by host pointers.** Each twin is found by a host pointer into guest memory (src/hd.c:139-149). Art comes from `DrawPicture` at the moment of drawing (src/hd.c:595-625). The screen twin alone is 30,720,000 bytes at 4x. Est. 40 to 120 MB in total.
- **D6, fast-forward still does output work.** While skipping draws, `watch_present` still runs `hd_frame` on every dirty present (src/watch.c:181-189). The mixer renders on every pump (src/sound.c:84-97). The exporter does the same during its seek (src/clip.c:617-623, 662-691).
- **D7, the exporter seeks by replaying from launch for every export** (src/clip.c:614-640).
- **D8, side effects on disk.** `CFPreferencesAppSynchronize` writes prefs.plist mid-game (src/cf.c:485-488). Game file writes copy the file into the data folder first (src/files.c:478-514).

Strengths: the replay is deterministic by construction. The clock comes from the file in whole ms, spin waits are counted rather than timed, and sound callbacks come from the file (src/replay.c:1063-1081, src/misc.c:189-233, src/sound.c:300-315). A frame hash of the 1x screen every 30 presents turns any desync into exit status 3 (src/main.c:98-108). Guest memory is one `mmap` (src/guest_mem.c:45) that Unicorn maps by pointer (src/cpu_unicorn.c:92-93), so the host can copy it without the Unicorn API and host pointers into it survive an in-place restore. The Memory Manager keeps its heap and every block header in guest memory, and its only host static is the last error code (src/memmgr.c:9-18, 25). The host patches code only at load (src/main.c:331-335). A replay runs on one thread, because live play's audio callback stream is never opened for it (src/sound.c:135-136), and it uses no file descriptor once loaded (src/replay.c:471). The mixer is integer-only (src/mixer.h:5-8). Headless runs already work (tests/test_main.c:214-215).

## Detailed findings, ranked by payoff

### Finding 1: A hybrid snapshot: raw guest pages, `uc_context`, and one tagged block per module

This is the central decision. There are three options.

**Per-module serializers.** Dolphin gives each subsystem one `DoState(PointerWrap&)` whose mode decides the direction. `DoVoid` memcpys buffer-to-object on Read, object-to-buffer on Write, and memcmps on Verify ([ChunkFile.h:37-57](https://github.com/dolphin-emu/dolphin/blob/8d2ad1a662472955497e5bb79d7b9ec6999e1f0d/Source/Core/Common/ChunkFile.h#L37-L57), [ChunkFile.h:362-391](https://github.com/dolphin-emu/dolphin/blob/8d2ad1a662472955497e5bb79d7b9ec6999e1f0d/Source/Core/Common/ChunkFile.h#L362-L391)). One hand-written root calls the subsystems in order ([State.cpp:139-203](https://github.com/dolphin-emu/dolphin/blob/8d2ad1a662472955497e5bb79d7b9ec6999e1f0d/Source/Core/Core/State.cpp#L139-L203)). Save and load list each field once, so they can't drift apart. FCEUX gets the same symmetry in C with static field tables of `{ptr, size, tag}` ([state.h:41-63](https://github.com/TASEmulators/fceux/blob/8cdbeeb248f5a13aa97a58b4a0437ae13fb6aea8/src/state.h#L41-L63)). BizHawk routes both directions through one `Action<Serializer>` ([StateSerializer.cs:12-52](https://github.com/TASEmulators/BizHawk/blob/c9de9a8bff0f95114df7e1d13d4dab820388dc60/src/BizHawk.Emulation.Common/Base%20Implementations/StateSerializer.cs#L12-L52)). RetroArch wraps blobs in a container of tagged blocks, each with a 32-bit length the reader bounds-checks before dispatch ([task_save.c:93-97](https://github.com/libretro/RetroArch/blob/664f389644eea9f91c10792198acf2c3770bad56/tasks/task_save.c#L93-L97), [task_save.c:1257-1411](https://github.com/libretro/RetroArch/blob/664f389644eea9f91c10792198acf2c3770bad56/tasks/task_save.c#L1257-L1411)). The cost is that every static must be listed by hand, and forgotten fields are a recurring bug class. Gecko's DoState carries a FIXME for state it doesn't save ([GeckoCode.cpp:217-227](https://github.com/dolphin-emu/dolphin/blob/8d2ad1a662472955497e5bb79d7b9ec6999e1f0d/Source/Core/Core/GeckoCode.cpp#L217-L227)).

**Whole-process checkpoints.** libTAS dumps the game process's own address space and needs no serializers at all. Save and load share one code path because a restore resumes inside `checkpoint()` ([SaveStateManager.cpp:403-451](https://github.com/clementgallet/libTAS/blob/32245db8e35ab8f2389bdb781e81ab5e5b92c4db/src/library/checkpoint/SaveStateManager.cpp#L403-L451)). The cost moves into a growing list of things outside memory that must be patched up: audio devices closed before every save and load ([SaveStateManager.cpp:317-324](https://github.com/clementgallet/libTAS/blob/32245db8e35ab8f2389bdb781e81ab5e5b92c4db/src/library/checkpoint/SaveStateManager.cpp#L317-L324), [SaveStateManager.cpp:465-472](https://github.com/clementgallet/libTAS/blob/32245db8e35ab8f2389bdb781e81ab5e5b92c4db/src/library/checkpoint/SaveStateManager.cpp#L465-L472)), the X connection copied aside and back ([Checkpoint.cpp:290-343](https://github.com/clementgallet/libTAS/blob/32245db8e35ab8f2389bdb781e81ab5e5b92c4db/src/library/checkpoint/Checkpoint.cpp#L290-L343)), threads suspended and re-created ([SaveStateManager.cpp:586-719](https://github.com/clementgallet/libTAS/blob/32245db8e35ab8f2389bdb781e81ab5e5b92c4db/src/library/checkpoint/SaveStateManager.cpp#L586-L719)), and UI config re-sent after every load because the game's copy was rolled back ([SaveState.cpp:214-219](https://github.com/clementgallet/libTAS/blob/32245db8e35ab8f2389bdb781e81ab5e5b92c4db/src/program/SaveState.cpp#L214-L219)). Its fork mode only makes saving asynchronous. The child writes files and exits, and never becomes the live game ([Checkpoint.cpp:1063-1072](https://github.com/clementgallet/libTAS/blob/32245db8e35ab8f2389bdb781e81ab5e5b92c4db/src/library/checkpoint/Checkpoint.cpp#L1063-L1072)). The macOS checkpoint port is unfinished: it opens `/proc/self/pagemap` without an `#ifdef` ([Checkpoint.cpp:405-406](https://github.com/clementgallet/libTAS/blob/32245db8e35ab8f2389bdb781e81ab5e5b92c4db/src/library/checkpoint/Checkpoint.cpp#L405-L406)) and uses an enum value that isn't defined ([MachVmMaps.cpp:65](https://github.com/clementgallet/libTAS/blob/32245db8e35ab8f2389bdb781e81ab5e5b92c4db/src/library/checkpoint/MachVmMaps.cpp#L65), [ReservedMemory.h:40-46](https://github.com/clementgallet/libTAS/blob/32245db8e35ab8f2389bdb781e81ab5e5b92c4db/src/library/checkpoint/ReservedMemory.h#L40-L46)). Apple's fork(2) man page says every framework should be assumed unsafe after fork until exec, and TN2083 says CoreFoundation detects the case and refuses.

**A hybrid.** BizHawk's Waterbox is the closest model. It saves all of a sandboxed core's memory, then appends a short list of host-side variables ([WaterboxCore.cs:279-316](https://github.com/TASEmulators/BizHawk/blob/c9de9a8bff0f95114df7e1d13d4dab820388dc60/src/BizHawk.Emulation.Cores/Waterbox/WaterboxCore.cs#L279-L316), [host.rs:170-195](https://github.com/TASEmulators/BizHawk/blob/c9de9a8bff0f95114df7e1d13d4dab820388dc60/waterbox/waterboxhost/src/host.rs#L170-L195)). The core's statics live in sandbox memory, so they need no field lists. BizHawk's QuickNES wrapper appends client counters after a native blob in the same way ([QuickNES.IStatable.cs:10-47](https://github.com/TASEmulators/BizHawk/blob/c9de9a8bff0f95114df7e1d13d4dab820388dc60/src/BizHawk.Emulation.Cores/Consoles/Nintendo/QuickNES/QuickNES.IStatable.cs#L10-L47)). RetroArch's run-ahead had to copy the whole core binary to disk and `dlopen` the copy to get a second set of statics ([runahead.c:301-310](https://github.com/libretro/RetroArch/blob/664f389644eea9f91c10792198acf2c3770bad56/runahead.c#L301-L310)). That is what file-scope statics cost when you need them twice.

The subject's facts decide it for the hybrid:

- Guest memory is one host `mmap` at a fixed address (src/guest_mem.c:45), and Unicorn maps it with `uc_mem_map_ptr` (src/cpu_unicorn.c:92-93). A memcpy captures it, and an in-place restore keeps every host pointer into it valid, including the HD twin keys. This is LittleWing's free Waterbox: the Memory Manager, QuickDraw's ports and PixMaps, and loaded resources all live there (src/memmgr.c:9-18, src/qd.c:117, 203, 379).
- Fourteen of the twenty emulation modules are plain fixed-size structs, such as misc `M` (src/misc.c:22-41), events `E` (src/events.c:53-87) and qd `Q` (src/qd.c:26-38). Their only pointers point at static code or data. Dolphin's own advice is to group a module's statics into one struct so its whole DoState is one call. Each of these becomes one block written with one `LW_DO(s, M)`.
- Six modules need real code. cf must deep-copy its objects and prefs (src/cf.c:31-46). dialogs must store its `front` pointer as an index (src/dialogs.c:107-116), and only matters while a dialog is open. cgimage must copy its pixels. files must store each `FILE*` as (rel, position, mode) and reopen it (src/files.c:48-57). The mixer can share its immutable `mix_sound`s by refcount (src/sound.c:247-255). HD is Finding 7.
- Fork would solve the restore-point problem in Finding 2 for free, because the host stack is in the checkpoint. But the core uses CoreFoundation at launch to read the prefs (src/plist.c:52-62), so any fork would come after it, and calls it again mid-game through `cf_save_prefs` (src/cf.c:485-488, src/plist.c:106-121). How macOS treats Unicorn's MAP_JIT translation buffer in a forked child, under the hardened runtime with allow-jit (src/cpu_unicorn.c:13, tools/make_app.sh:179), is unverified. Using it would need the biggest refactor on the table: moving watch.c's pacing, the display, the sound monitor, the menu and the export child into a separate UI process. Each checkpoint would also pin the 30 MB HD screen twin, because the game rewrites it constantly.

The prescription is a walker, `struct lw_state { uint8_t *cur, *end; enum { READ, WRITE, MEASURE, VERIFY } mode; bool failed; }`. Use `lw_do(s, ptr, n)` and an `LW_DO(s, field)` macro, and use a separate `failed` flag rather than Dolphin's mode-as-error-channel. A static table `{tag, fn}` lists the modules in a fixed order, with the reason for each ordering constraint written beside it, as Dolphin does ([State.cpp:172-192](https://github.com/dolphin-emu/dolphin/blob/8d2ad1a662472955497e5bb79d7b9ec6999e1f0d/Source/Core/Core/State.cpp#L172-L192)). Each module writes one tagged, length-prefixed block. Guest pages and `uc_context` (src/cpu_unicorn.c:212-218) are two more blocks. After every block is in place, a separate `post_load` pass rebuilds derived state. The first item in it is a Unicorn translation cache flush (`uc_ctl_flush_tb`), the same move as Dolphin clearing its JIT cache on Read ([JitInterface.cpp:41-45](https://github.com/dolphin-emu/dolphin/blob/8d2ad1a662472955497e5bb79d7b9ec6999e1f0d/Source/Core/Core/PowerPC/JitInterface.cpp#L41-L45)). The code bytes don't change after load, so the flush is defensive. But the image region holds code and data on the same RWX pages (src/guest_mem.c:17), and a host memcpy bypasses QEMU's dirty-code tracking. Retranslating 280 KB of code is cheap. Leave hooks in the live engine. The viewer, display, menu, export, clip and script modules stay out of the snapshot, as RetroArch's rewind leaves out frontend blocks ([task_save.c:539-548](https://github.com/libretro/RetroArch/blob/664f389644eea9f91c10792198acf2c3770bad56/tasks/task_save.c#L539-L548)).

Est. size per snapshot, without HD: 5 to 25 MB of resident guest pages out of 80.06 MiB mapped, plus tens of KB for `uc_context` and under 400 KB of module structs. Measure resident pages with `mincore()` over `gm_host_base()`. Confidence: high. Five references converge on this boundary from different directions, and the subject's memory layout makes the raw part nearly free. The two risks are split out as Findings 2 and 7.

### Finding 2: Capture and restore only at a trap entry at depth 1, with a re-entry path for the end

Every reference confines state work to one clean boundary. Dolphin's `RunOnCPUThread` pauses the CPU and runs the job at the top of the CPU run loop, between slices ([Core.cpp:825-849](https://github.com/dolphin-emu/dolphin/blob/8d2ad1a662472955497e5bb79d7b9ec6999e1f0d/Source/Core/Core/Core.cpp#L825-L849), [CPU.cpp:118-122](https://github.com/dolphin-emu/dolphin/blob/8d2ad1a662472955497e5bb79d7b9ec6999e1f0d/Source/Core/Core/HW/CPU.cpp#L118-L122)). libTAS checkpoints only at frame boundaries on the main thread, after every thread has left its hook wrappers ([SaveStateManager.cpp:310-311](https://github.com/clementgallet/libTAS/blob/32245db8e35ab8f2389bdb781e81ab5e5b92c4db/src/library/checkpoint/SaveStateManager.cpp#L310-L311), [ThreadSync.cpp:45-54](https://github.com/clementgallet/libTAS/blob/32245db8e35ab8f2389bdb781e81ab5e5b92c4db/src/library/checkpoint/ThreadSync.cpp#L45-L54)). RetroArch's rewind steps between frames on the main thread and refuses to start when the core has a threaded audio callback ([state_manager.c:802-807](https://github.com/libretro/RetroArch/blob/664f389644eea9f91c10792198acf2c3770bad56/state_manager.c#L802-L807)).

LittleWing has no frame loop to put that boundary in, so the boundary has to be a trap. In `guest_call`, after `cpu_run` stops at a trap and before `T.handlers[index]()` runs (src/trap.c:188-217), the only host frames at depth 1 are `main` and `guest_call`, and every handler local is dead. Snapshot there, and record the trap index and the resume address with the snapshot. A restore loads the state, then dispatches that same handler and continues from the restored resume address. Never snapshot or restore at depth 2 or more: inside a sound callback (src/sound.c:297), a Carbon timer (src/events.c:348-354) or a modal dialog loop (src/dialogs.c:606). Loony spins on TickCount and Delay(0) (src/misc.c:189-193), so depth-1 trap entries should come often, provided its loop runs at depth 1. The code reading suggests it does, but nothing has measured it, and Spike A checks it.

A seek request from a key or a menu item only records the target, and the work happens at the next depth-1 trap entry. Don't longjmp out of AppKit callbacks inside `SDL_PollEvent` (src/menu.m:217-233). If the viewer is paused inside `pace` (src/watch.c:273-276), a pending seek must make `pace` return so the guest runs to the next trap. The end of a replay needs a re-entry path. `watch_hold` loops either after the game's `main` returned, at depth 0 (src/main.c:186-188), or inside a trap through `replay_step` and `R.end` (src/replay.c:1050-1056). At depth 0, restore and run a resume loop shaped like `guest_call`'s body, starting from the restored context. From inside a trap, set the request, let `watch_hold`'s plain C loop see it, and unwind with a longjmp to a `setjmp` placed in `main` before the guest call. Then restore and enter the same resume loop. No `uc_emu_start` is on the stack while a handler runs. A trap is a fetch from an unmapped address, the invalid-memory hook returns false, and `uc_emu_start` has returned before `guest_call` dispatches (src/cpu_unicorn.c:34-43, 170-187). That holds at every depth, because a nested `guest_call` starts its own `cpu_run` from inside a handler. The Unicorn hooks that do run host code inside `uc_emu_start` only set flags, and play.c's are not installed on a replay (src/play.c:53-55). Never service a seek from inside a hook: a longjmp from there would cross `uc_emu_start`, which is unsafe, and a hook may only call `uc_emu_stop` and return. The longjmp skips every `guest_call` frame between the handler and `main`, so reset `T.depth` and accept the leaked per-call `cpu_context`, one per nesting level, or free them.

The first spike: snapshot at a depth-1 trap entry at tick N, run on, restore at a later depth-1 entry, and replay to the end. Require "no desync". The replay's own frame hashes check the result for free. Confidence: medium. The reasoning comes from reading the code, and nothing was run. This rule also limits the design to games whose loop runs at depth 1. That is fine, because replays are Loony-only (src/main.c:365).

### Finding 3: A seek is a target the emulation loop polls

BizHawk's `GoToFrame` sets the target, fetches the closest state at or before `frame - 1`, loads it only if the target is behind or the state is ahead of the live frame, and runs forward ([TAStudio.Navigation.cs:11-58](https://github.com/TASEmulators/BizHawk/blob/c9de9a8bff0f95114df7e1d13d4dab820388dc60/src/BizHawk.Client.EmuHawk/tools/TAStudio/TAStudio.Navigation.cs#L11-L58)). It keeps capturing states during the run, so a second scrub over the same stretch is fast ([MovieSession.cs:108-119](https://github.com/TASEmulators/BizHawk/blob/c9de9a8bff0f95114df7e1d13d4dab820388dc60/src/BizHawk.Client.Common/movie/MovieSession.cs#L108-L119)). Slippi computes the nearest keyframe and loads it only when that beats fast-forwarding from where it is ([SlippiPlayback.cpp:245-284](https://github.com/project-slippi/Ishiiruka/blob/60f7b63496fb6ec7b9180a04f16f3edc0ad89fe2/Source/Core/Core/Slippi/SlippiPlayback.cpp#L245-L284)). It remembers whether it was paused and resumes only if it wasn't ([SlippiPlayback.cpp:225-226](https://github.com/project-slippi/Ishiiruka/blob/60f7b63496fb6ec7b9180a04f16f3edc0ad89fe2/Source/Core/Core/Slippi/SlippiPlayback.cpp#L225-L226), [SlippiPlayback.cpp:298-303](https://github.com/project-slippi/Ishiiruka/blob/60f7b63496fb6ec7b9180a04f16f3edc0ad89fe2/Source/Core/Core/Slippi/SlippiPlayback.cpp#L298-L303)). asciinema-player replays forward when the target is in the active segment, and otherwise restores the target's segment ([recording.js:1261-1281](https://github.com/asciinema/asciinema-player/blob/fc82c581a10c6ae034517ad62323dea1a5ddb237/src/driver/recording.js#L1261-L1281)). Its `positionGeneration` counter goes up on every operation that moves the playhead, and each continuation returns once it is stale ([recording.js:1334](https://github.com/asciinema/asciinema-player/blob/fc82c581a10c6ae034517ad62323dea1a5ddb237/src/driver/recording.js#L1334), [recording.js:813-839](https://github.com/asciinema/asciinema-player/blob/fc82c581a10c6ae034517ad62323dea1a5ddb237/src/driver/recording.js#L813-L839)). `resumeAfterSeek` carries play or pause across the seek ([recording.js:1329-1364](https://github.com/asciinema/asciinema-player/blob/fc82c581a10c6ae034517ad62323dea1a5ddb237/src/driver/recording.js#L1329-L1364)). FCEUX falls back to an earlier state if a load fails, and never trusts the live state after a failed load ([playback.cpp:446-512](https://github.com/TASEmulators/fceux/blob/8cdbeeb248f5a13aa97a58b4a0437ae13fb6aea8/src/drivers/win/taseditor/playback.cpp#L446-L512)). libTAS has the same shape: the nearest state at or before the target, then run to `seek_frame` ([InputEditorModel.cpp:1286-1350](https://github.com/clementgallet/libTAS/blob/32245db8e35ab8f2389bdb781e81ab5e5b92c4db/src/program/ui/InputEditorModel.cpp#L1286-L1350)).

This replaces `go_back` and the forward-only `W.from`/`W.going` pair in `step_by` (src/watch.c:324-370). Keep one engine struct: `target_tick`, `gen`, `resume_playing`, and an explicit state enum, as asciinema's `transition()` does ([recording.js:22-54](https://github.com/asciinema/asciinema-player/blob/fc82c581a10c6ae034517ad62323dea1a5ddb237/src/driver/recording.js#L22-L54)). A request writes the target and bumps `gen`. At the next depth-1 trap entry the engine checks whether the live tick is at or before the target and closer than the best snapshot. If so, it just fast-forwards, which is today's `W.going`. Otherwise it restores. During fast-forward it rechecks `gen` at each trap entry, so a newer target takes over without finishing the old one. When it arrives, it re-anchors pacing and restores the remembered play or pause. Treat boot as snapshot 0, as asciinema-player models an unsegmented recording as one segment starting at 0 ([full.js:14-41](https://github.com/asciinema/asciinema-player/blob/fc82c581a10c6ae034517ad62323dea1a5ddb237/src/driver/recording/full.js#L14-L41)), so one code path covers every seek. This is the engine side of the UI report's Finding 2 (newest target wins, progress overlay with cancel). Its determinate bar can use BizHawk's progress formula. Confidence: high. Five references agree, and it fits LittleWing's single thread.

### Finding 4: Prove every restore with a harness

### Finding 6: Share unchanged guest pages between snapshots

RetroArch's statestream splits replay checkpoints into fixed blocks, interns each block in a hash index, and writes a checkpoint as its new blocks plus a sequence of block IDs ([task_movie.c:57-62](https://github.com/libretro/RetroArch/blob/664f389644eea9f91c10792198acf2c3770bad56/tasks/task_movie.c#L57-L62), [bsvmovie.c:1730-1800](https://github.com/libretro/RetroArch/blob/664f389644eea9f91c10792198acf2c3770bad56/input/bsv/bsvmovie.c#L1730-L1800)). Waterbox saves only pages dirtied since the core was sealed ([memory_block/mod.rs:878-914](https://github.com/TASEmulators/BizHawk/blob/c9de9a8bff0f95114df7e1d13d4dab820388dc60/waterbox/waterboxhost/src/memory_block/mod.rs#L878-L914)). libTAS stores a zero page as one flag byte ([Checkpoint.cpp:1327-1367](https://github.com/clementgallet/libTAS/blob/32245db8e35ab8f2389bdb781e81ab5e5b92c4db/src/library/checkpoint/Checkpoint.cpp#L1327-L1367)), and lets a clean page inherit its parent's copy ([Checkpoint.cpp:1424-1474](https://github.com/clementgallet/libTAS/blob/32245db8e35ab8f2389bdb781e81ab5e5b92c4db/src/library/checkpoint/Checkpoint.cpp#L1424-L1474)). Slippi VCDIFF-encodes every keyframe against the first state, so any keyframe decodes from that state alone ([SlippiPlayback.cpp:41-54](https://github.com/project-slippi/Ishiiruka/blob/60f7b63496fb6ec7b9180a04f16f3edc0ad89fe2/Source/Core/Core/Slippi/SlippiPlayback.cpp#L41-L54)). RetroArch's rewind codec stores reverse deltas, which leaves no random access: reaching k states back costs k decodes and pops them ([state_manager.c:630-671](https://github.com/libretro/RetroArch/blob/664f389644eea9f91c10792198acf2c3770bad56/state_manager.c#L630-L671)).

Pick block sharing. A Loony snapshot's bulk is guest pages, and most of them stay the same between snapshots: loaded resources, code, and the 480,000-byte screen when nothing moves. Store each snapshot's guest RAM as a list of refs into a refcounted pool of 4 KiB pages. At capture, memcmp each resident page against the previous snapshot's page, reuse the ref when they match, and store all-zero pages as a flag. That keeps every snapshot one decode from complete, as Slippi's scheme does, without its growing distance from boot as the heap fills, and without a VCDIFF dependency. Charge the budget in unique pages. Evicting a snapshot then decrements refs and may free little, and the store has to accept that. Ship v1 with full copies if Finding 5's measurements show the budget holds enough snapshots, and add sharing when it doesn't. Est. 1 to 5 MB per snapshot with sharing, so 240 snapshots an hour at 15 s spacing cost 0.25 to 1.2 GB before tiering. Confidence: medium. The approach is well proven, but Loony's dirty-page rate is unmeasured.

### Finding 7: Rebuild HD output after a restore

None of the references snapshots a renderer's private output. libTAS can't checkpoint GPU state and requires software rendering ([faq.md:28-44](https://github.com/clementgallet/libTAS/blob/32245db8e35ab8f2389bdb781e81ab5e5b92c4db/docs/faq.md#L28-L44)), and after a load the UI asks the game to redraw ([SaveState.cpp:205-272](https://github.com/clementgallet/libTAS/blob/32245db8e35ab8f2389bdb781e81ab5e5b92c4db/src/program/SaveState.cpp#L205-L272)). asciinema-player throws away the terminal and rebuilds it from the snapshot, so no stale field survives ([vt.js:25-36](https://github.com/asciinema/asciinema-player/blob/fc82c581a10c6ae034517ad62323dea1a5ddb237/src/vt.js#L25-L36)). BizHawk loads one frame early and emulates one frame to get a real picture ([TAStudio.cs:1083-1103](https://github.com/TASEmulators/BizHawk/blob/c9de9a8bff0f95114df7e1d13d4dab820388dc60/src/BizHawk.Client.EmuHawk/tools/TAStudio/TAStudio.cs#L1083-L1103)). FCEUX takes the other road and stores its 64 KB back buffer in every state ([state.cpp:416-424](https://github.com/TASEmulators/fceux/blob/8cdbeeb248f5a13aa97a58b4a0437ae13fb6aea8/src/state.cpp#L416-L424)), which is affordable only because it is small.

LittleWing's HD twins can't be stored per snapshot. Est. 40 to 120 MB at 4x, multiplied by hundreds of snapshots, is gigabytes. Dropping them is visible: the table would show blocky pixels until the game redraws its PICTs (src/hd.c:595-625). But a twin already records part of what a rebuild needs. A larger buffer with art keeps its 1x pixels just after the art was drawn, the art's index and where it went (src/hd.c:29-35). Its sync puts the art back on any pixel that has returned to that original value (src/hd.c:372-387). The art cache only grows and is keyed by picture hash, so it can survive restores unchanged (src/hd.c:527-565). Two things are not recorded. A sprite keeps no art index or destination, because `hd_picture` returns before setting them (src/hd.c:614-617), and `match_sprite` skips a sprite whose `ref` doesn't match its pixels, which a fresh twin's never does (src/hd.c:157-158, 257-258). HD pixels that reached a buffer through `hd_copy` aren't recorded anywhere, so they come back only when the game copies them again. So store a per-twin recipe: guest address of `base`, bounds, depth, row bytes, `sprite`, `orig`, `orig_art`, `orig_dst` and `orig_area`, plus an art index and destination for each sprite, which the code would have to start keeping. Est. hundreds of KB to a few MB at 8 bpp, since `orig` is a full 1x copy of each large buffer with art. On restore, build a fresh twin from the recipe, draw the art, and let the normal sync redraw everything else from the restored 1x pixels. The screen's HD pixels come from copies, so they return on the game's next copy of the table, which the copy code says it often does whole, each frame (src/hd.c:469-471).

This is an inference from the code, and it may not hold. `orig_art` holds one art per twin, so a buffer that received several pictures keeps only the last. Spike it: restore with the recipe and compare the HD screen against the straight run at the same tick. If it fails, the fallback is full HD twins in a few sparse "HD snapshots" only, with plain snapshots accepting blocky HD until the next redraw. The exporter's HD scale of 2 (src/clip.c:994-996) costs a quarter as much. The desync hash reads the 1x screen (src/main.c:98-108), so none of this affects verification. Confidence: low until the spike runs.

LittleWing's input log is immutable, fully decompressed into `R.data`, and opening another replay restarts the process today. So v1 snapshots stay in memory, and invalidation is the process lifetime plus one epoch counter bumped on any discontinuity that isn't a seek within the same replay. A snapshot carries the replay cursor (`R.step`, `R.clock_ms`, `R.presents`, `R.frames_checked`, `R.marks`, `R.in.pos`, `R.next`, `cut_short`, `reached_end`, src/replay.c:79-111), not the log. Assert on restore that its tick and `R.in.pos` agree, as asciinema-player validates its index ([segmented.js:79-130](https://github.com/asciinema/asciinema-player/blob/fc82c581a10c6ae034517ad62323dea1a5ddb237/src/driver/recording/segmented.js#L79-L130)). prefs.plist is a side effect, and the in-memory prefs in cf's block are the state. The game reads prefs only at launch through `cf_load_prefs` (src/main.c:388-391), so a restore doesn't touch the file. Verify that Loony writes no other data files. Persisting snapshots next to a replay, which would let the exporter skip its seek from launch (D7), is a later step. It needs a header with build ID, game ID and layout hash that rejects any mismatch, as Waterbox's sealed-image hash does ([memory_block/mod.rs:833-850](https://github.com/TASEmulators/BizHawk/blob/c9de9a8bff0f95114df7e1d13d4dab820388dc60/waterbox/waterboxhost/src/memory_block/mod.rs#L833-L850)). Confidence: high.

## Where the subject already matches or beats the references

- The recording carries a frame hash every 30 presents, and any mismatch is a desync with exit status 3. Dolphin's movies carry no per-frame hash, Slippi has no host-side check, and libTAS's hash check is commented out. Only RetroArch's netplay CRC comes close, and it runs only between peers.
- A replay runs on one thread. It avoids Slippi's shared-flag races and the mutex history Dolphin had to cut down.
- Guest memory is mapped once at a fixed host address, so an in-place restore faces none of libTAS's layout drift: stacks that grew, heaps resized with `brk`, overlapping mappings ([Checkpoint.cpp:497-743](https://github.com/clementgallet/libTAS/blob/32245db8e35ab8f2389bdb781e81ab5e5b92c4db/src/library/checkpoint/Checkpoint.cpp#L497-L743)). It is the same property Waterbox builds a sandbox to get.
- Determinism is pinned at the source. The clock comes from the file in whole ms, spin waits are counted, and sound callbacks come from the file. Dolphin needs a global determinism mode that reconfigures subsystems.
- The desync hash reads only the 1x screen, which is RetroArch's "hash only the deterministic part" ([netplay_frontend.c:2430-2439](https://github.com/libretro/RetroArch/blob/664f389644eea9f91c10792198acf2c3770bad56/network/netplay/netplay_frontend.c#L2430-L2439)) by construction. HD and the mixer sit outside it.
- The replay is decompressed into memory once and uses no file descriptor during playback. RetroArch rescans its replay file from the start on every checkpoint seek.
- A second process with a progress protocol on a pipe already exists, the exporter (src/export.c:218-300). It is the same split libTAS draws between UI and game, if a core process is ever wanted.

## Recommended execution order

1. **Measure.** Log resident guest pages with `mincore()`, `uc_context_size`, HD twin count and bytes at 4x, and unpaced replay speed with and without HD sync and mixer rendering. Every size in this report is an estimate until this lands. The Amendments add two items here: a histogram of trap depth at trap entries, and the copy-on-write remap spike.
2. **Spike A, restore at a depth-1 trap entry.** Headless, Loony, HD off. Capture guest pages, `uc_context` and every emulation module's statics crudely, at tick N. Run on, restore at the next depth-1 trap entry, flush the translation cache, and replay to the end. Pass means "no desync" and frame hashes that match. Nothing else gets built until this passes.
3. **Spike B, the end-of-replay re-entry.** Seek back from `watch_hold`, both after `main` returns and from `R.end` inside a trap. Pass means the same.
4. **Spike C, HD recipe rebuild.** Compare the restored HD screen with the straight run at the same tick. Its result picks Finding 7's path or its fallback. If Spike A fails for a reason the depth-1 rule can't fix, test fork with MAP_JIT under the hardened runtime before considering a core process.
5. **The walker and registry.** Add tagged blocks, markers, length checks, zeroing and Verify mode, then convert the fourteen plain modules and the six heap modules. Add Finding 4's round-trip unit test in the same step.
6. **The store**, in the small v1 form the Amendments describe, as a standalone module with unit tests on fake blobs, including long synthetic runs. The tiers, the gap rule and `is_reserved` only if step 1's numbers call for them.
7. **The seek controller.** Target, `gen`, skip-if-closer and play/pause restore, replacing `go_back`. Rewrite the two restart tests deliberately in this commit, and add the seek-across-a-snapshot integration test.
8. **Output suppression** (Finding 8), with the speed measured before and after.
9. **Page sharing** (Finding 6), if step 1 and real use show the budget is short.
10. **Later.** Persisted snapshots for the exporter, behind a build-ID header. With cheap back seeks, revisit the UI report's Finding 2 and Finding 6: live scrubbing, and arrows that seek back 5 s and comma for a frame back, become affordable once the New tier is dense.

## Refactor notes

- **Boundaries.** Nothing drawn for the viewer may reach `screen_rgba` or the frame hashes. Snapshot capture must not change any emulation state, so a replay with snapshots on produces the same hashes as one with them off.
- **Recording format stays.** Snapshots are in-memory engine state, and the `.lwreplay` format, its header and its records don't change. Cmd-S capture during play stays as it is.
- **Loony only.** Replays are Loony Labyrinth only (src/main.c:365). Loony's own loop turned out to run inside a `RunApplicationEventLoop` timer callback (src/events.c:728-742; see Measurements), so the boundary is a depth-2 trap entry there. MONSTER FAIR would need its own measurement, and that is not a reason to generalize it now. Don't test or enable this for other games.
- **Tests that change on purpose.** `run_a_watched_replay_goes_ahead_and_back` asserts the restart log lines "watch: back to 0:00: restarting" and "loony: watch: restarting the replay" (tests/test_run.c:969-1001). `run_a_watched_replay_keeps_exporting_when_it_goes_back` asserts the export is handed over through the restart (tests/test_run.c:1094-1127). Rewrite both in the seek-controller commit, with new assertions for an in-place seek, and say so in the commit message. Every other replay test, and the golden frame and WAV hashes, is the invariant.
- **Steps and commits.** Verify and commit per step. Two consecutive failures on one step stop the work for a re-plan.
